## 0. 分支与版本策略

| 项 | 做法 |
|---|---|
| 主分支 | `main` 保持受保护：required check `build` + `enforce_admins=true`，不直接 push |
| 开发分支 | 从 `origin/main`（当前 `b1243ba`）新建 **`feat/v0.5.0`**，全部开发与测试提交都在这条线上 |

| 发布正式版 | 用户真机验收通过后，才把版本改成 `0.5.0` 并打 tag `V0.5.0` |

### T2 · #44

- 根因（已本地复现）：`src/service/launcher.ts:138 desktopRootFromShim()` 硬编码 `DeepSeek Harness` 目录名，自定义根 `D:\dsh` 被判成 npm shim → `bin.js` 不存在 → 丢弃 → Desktop PATH 兜底同样被过滤 → `resolveLaunch()` 返回 `null`。
- 修法：A 判据结构化（`<任意根>\resources\runtime\cli\bin\dsh.cmd`）+ B 最后兜底（PATH 命中但推不出 bin.js 时按 cmd 脚本执行）。
- 测试：自定义根、标准根回归、npm 优先、bin.js 缺失回退、大写扩展名、含空格路径、版本探测。
- 用户侧临时绕过：`dsh.desktopCommandPath` 填 `D:\dsh\resources\runtime\cli\bin\dsh.cmd`（当前版本即可用）。

### T3 · 集成②编辑器标签页（对应图2/图3）

- 现状：`dsh.openFromTitle`（编辑器标题栏图标）调用 `openSecondary()` → 打开右侧辅助侧边栏。
- 目标：改成在**编辑器区开一个 WebviewPanel 标签页**，像 Claude Code 那样当场打开。
- 实现参考（PR #38，未合并）：把 `resolveWebviewView` 的绑定逻辑抽成 `resolveWebview(webview)`，新增 `detach()`；`WebviewPanel` 用 `retainContextWhenHidden` 常驻，关标签只解绑不重建；首次渲染后主动 `handleStateChange()` 解决 401。
- 风险：多 webview 实例与桥接握手状态；标签页关闭后的资源/会话清理；`retainContextWhenHidden` 内存占用。
- 待定：是否保留「在侧边栏打开」命令（建议保留 `dsh.openSecondary`），是否加设置项（建议先不加，默认就是编辑器标签页）。

### T4 · 集成③资源管理器右键 → 加入 DSH 对话（对应图4）

- 现状：桥接只支持「页面 → 编辑器」方向（openFile / copyText / saveImage 等），没有「编辑器 → 页面输入框」。
- 目标：`explorer/context` 加菜单（按你的描述做成二级子菜单「DSH」→「添加到对话」），把选中文件以引用形式插入 DSH 输入框。
- 实现：新命令 → 打开/复用面板 → 宿主向页面下发新消息 `insertFileMention` → 桥接聚焦 composer 并插入 `@相对路径`（复用已有的 `insertTextIntoFocused` 思路）。
- 风险（需真机 spike）：DSH 输入框是 Lexical 富文本，纯文本 `@路径` 不一定被解析成引用芯片；多选/多根工作区的相对路径基准；面板未就绪时的时序。
- 兜底：注入失败时退回「复制路径到剪贴板 + 提示」。

## 3. 集成①「在聊天界面选中 DSH」——**已取消（2026-11-21 用户决定）**

> 用户决定：本条不做（对应原路线 D）。以下证据留档，将来 VS Code 若把 `chatSessionsProvider` 转为稳定 API，可据此重新评估。

**原结论：图1 那个下拉（本地 / Copilot / Claude / Cloud / Codex）目前第三方扩展进不去。**

**结论：图1 那个下拉（本地 / Copilot / Claude / Cloud / Codex）目前第三方扩展进不去。**

证据（全部来自本机 VS Code **1.145.2** 的运行时产物，非猜测）：

1. 该下拉的数据源是 `contributes.chatSessions` 扩展点；`copilot`、`github` 两个内置扩展在用它（条目形如 `type:"copilotcli"`、`displayName:"Copilot CLI"`）。
2. 但这条贡献**只有在扩展启用了 proposed API `chatSessionsProvider` 时才会被注册**：
   运行时里有过滤函数 `dl(ext, "chatSessionsProvider")` → 读 `ext.enabledApiProposals`；未声明直接跳过。
3. `chatSessionsProvider` 属于 **proposed API**：正式 `@types/vscode@1.145.0` 里没有 `ChatSession*` 任何符号，运行时把它映射到 `vscode.proposed.chatSessionsProvider.d.ts`。
4. proposed API 有**白名单**，目前只对内置扩展与少数合作方开放（实测白名单里 `GitHub.vscode-pull-request-github`、`openai.chatgpt` 等有 `chatSessionsProvider`，没有第三方）。
5. 下拉里的 Claude / Codex 条目来自 VS Code **核心内置的 agent-host 类型**（运行时枚举：`copilotcli` / `copilot-cloud-agent` / `cloud-sandbox` / `local` / `openai-codex` / `agent-host-claude` / `agent-host-codex`），不是第三方扩展贡献的。

**可选路线**

| 路线 | 效果 | 可行性 | 代价 |
|---|---|---|---|
| **A. Chat Participant（`@dsh`）** | 在 VS Code 聊天视图里输入 `@dsh` 与 DSH 对话，出现在 `@` 选择器里 | ✅ 稳定 API，可上架 | 中高：需要打通「扩展 → DSH 会话」的程序化通道（DSH 内部 RPC 或 CLI），且没有独立会话列表 |
| **B. proposed API（`chatSessionsProvider`）** | 图1 的完整效果：下拉里出现 DSH、会话列进 Agents/Sessions 视图 | ⚠️ 只在你本机可用 | 需以 `--enable-proposed-api fengze233.dsh-vscode-panel` 启动 VS Code；**上架版对普通用户不生效**；还要自行实现 provider + 内容渲染 |
| **C. 申请 VS Code 官方白名单** | 真·上架且进下拉 | ❓ 不可控 | 周期与结果都不确定，不建议作为版本目标 |
| **D. 不做聊天内嵌，改由集成②满足** | 点开就在编辑器标签页里用完整 DSH | ✅ 本版已覆盖 | 与 Copilot/Claude 的「同一个聊天框」体验仍有差距 |

**建议**：先把 A 当作可上架的目标做 spike（先验证 DSH 有没有可用的程序化收发通道）；B 作为「本机增强」可选开关（运行时特性探测，探测不到就不注册）；C 不排期。**这一条需要你选 A / B / D 后再动工。**
